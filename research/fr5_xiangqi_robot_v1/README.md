# FR5 Xiangqi Robot

An autonomous Xiangqi (Chinese Chess) playing robot system combining overhead camera sensing, YOLO-based board state occupancy detection, a Pygame UI interface, a chess AI engine, and physical robotic manipulation. The runtime is currently deployed for the **Fairino FR5** collaborative robot utilizing a **JODELL/ERG** gripper via SDK commands, though the hardware, camera, and physical board coordinate alignments must be calibrated for each unique physical environment.

> **Note:** The parameters in `config.py` serve as a reference setup. Camera IP address, workspace offsets, vertical pick/place clearance heights, gripper position limits, and API tokens must be tailored to your specific hardware and physical chessboard configuration.

---

## 1. System Architecture

```text
Camera / Video Source
        ↓
YOLO occupancy model + perspective transform
        ↓
SnapshotDetector: compares T1 baseline with T2 after pressing SPACE
        ↓
GameState + Xiangqi rules + FEN representation
        ↓
AI Chess Engine → Robot motion planning → Update T1 baseline
```

Key Components:

| Module | Role |
|---|---|
| `main.py` | Main event loop: coordinates UI, user inputs, AI evaluation, robot movement, and baseline capture. |
| `config.py` | Runtime configuration: camera stream URLs, robot IP, gripper limits, and chessboard coordinates. |
| `src/core/` | Game state, FEN parsers, move validators, and move rollback logic. |
| `src/vision/` | Video capture, YOLO occupancy inference, perspective transformation, and snap-difference detector. |
| `src/hardware/` | Robot TCP communication interface, gripper controllers, and Fairino SDK hardware manager. |
| `src/ai/` | Cloud engine connector and local Moonfish chess engine bridge. |
| `src/ui/` | Pygame graphical chessboard, interface control buttons, and keyboard/mouse handlers. |
| `tests/` | Manual testing scripts, hardware calibration utilities, and isolated verification tools. |

## 4. Required Assets

### 4.1. YOLO Model Weights
The system looks for model weights at `assets/models/best.pt`.
You can check if the file is loaded correctly by running:
```python
from ultralytics import YOLO
model = YOLO("assets/models/best.pt")
print("YOLO model verified successfully.")
```
If using custom piece designs, cameras, or ambient lighting setups, it is recommended to create a custom dataset and train a new occupancy detection model.

### 4.2. Perspective Calibration
The matrix is saved to `assets/perspective.npy`. This file represents the homography projection from the camera's raw perspective view to a flat, normalized chessboard grid. When changing the camera position, angle, resolution, or the chessboard itself, recalculate this matrix by running the warp tool and selecting the corner points in the following sequence:
1. **R1:** Black Left (column 0, row 0)
2. **R2:** Black Right (column 8, row 0)
3. **R3:** Red Right (column 8, row 9)
4. **R4:** Red Left (column 0, row 9)

### 4.3. Local Chess Engine
A local engine is only required if `ENGINE_TYPE` is set to `"LOCAL"` or `"HYBRID"`.
```bash
git clone https://github.com/walker8088/moonfish.git moonfish
```
The config currently supports Moonfish Python implementation:
```python
MOONFISH_EXE = "moonfish/moonfish_ucci.py"
MOONFISH_NNUE = None
```

## 5. Runtime Configuration (`config.py`)

The `config.py` file contains the primary variables that need tuning when adapting this project to a new physical setting.

### 5.1. Execution Mode
```python
DRY_RUN = True
```
- `True`: Dry run mode. The system does not attempt connection to the physical robot. Used to test the UI, game rules, and AI engine simulation via mouse clicks.
- `False`: Production mode. Connects to the camera stream, runs real-time YOLO detection, and sends motion commands to the physical robot.

### 5.2. Camera and Video Stream
```python
VIDEO_SOURCE = "http://10.64.218.131:4747/video"
VIDEO_BUFFER_SIZE = 1
```
Change `VIDEO_SOURCE` based on your camera hardware:
- `0, 1, 2` (Integers): USB webcam indices.
- `"http://x.x.x.x:4747/video"`: DroidCam or other network IP camera stream.
- `"path/to/video.mp4"`: Local video file path for testing and debugging.

To test the camera stream setup:
```bash
python tests/00_camera/test_video_source.py --show
```

### 5.3. Robot Network Interface
```python
ROBOT_IP = "192.168.58.2"
```
Set this value to the IP address of your robot controller. Verify connectivity via:
```bash
ping -c 3 192.168.58.2
nc -vz 192.168.58.2 20003
```
*Tip: If using Docker, ensure the default Docker bridge subnets do not conflict with the robot controller IP route.*

### 5.4. Board Coordinate Fallbacks
Logical board coordinates:
- Columns: `0..8`
- Rows: `0..9`
- Corner mappings: R1=`(0,0)`, R2=`(8,0)`, R3=`(8,9)`, R4=`(0,9)`

If explicit teaching points are missing, coordinate mapping falls back to linear spacing scalars:
```python
ROBOT_COL_TO_X_SIGN = 1
ROBOT_ROW_TO_Y_SIGN = -1
CELL_SIZE_COL_MM = 326.0 / 8.0
CELL_SIZE_ROW_MM = (370.0 - 2.0) / 9.0
```
Production runs calculate target coordinates using bilinear interpolation mapped directly from the physical teaching points `R1`/`R2`/`R3`/`R4`.

### 5.5. Gripper Offset Calibration
```python
OFFSET_X = 4.0
<ctrl94> **Note:** The parameters in `config.py` serve as a reference setup. Camera IP address, workspace offsets, vertical pick/place clearance heights, gripper position limits, and API tokens must be tailored to your specific hardware and physical chessboard configuration.
OFFSET_Y = 0.0
```
- **Positive `OFFSET_X`**: Moves the gripper TCP closer to the R2/R3 side.
- **Negative `OFFSET_X`**: Moves the gripper TCP closer to the R1/R4 side.
- **Positive `OFFSET_Y`**: Moves the gripper TCP closer to the robot base.
- **Negative `OFFSET_Y`**: Moves the gripper TCP further away from the robot base.

### 5.6. Vertical Clearance (Z Height) and Orientation
```python
SAFE_Z  = 286.869
PICK_Z  = 181.477
PLACE_Z = 190.0
ROTATION = [-180.0, 0.0, -180.0]
```
These parameters depend directly on the height of your table, the dimensions of the chess pieces, your gripper jaw extension length, and tool center point (TCP) definitions.
Recommended tuning sequence:
1. `SAFE_Z`: Height at which the robot can traverse the board without colliding with any standing pieces.
2. `PICK_Z`: Lower limit where the gripper fingers can safely close on a piece without contacting the table surface.
3. `PLACE_Z`: Height at which the robot releases the piece, ensuring a stable release without forcing the piece down into the board.
4. `ROTATION`: Align orientation with your physical chessboard layout.

### 5.7. Gripper Controls
Configured for the JODELL/ERG EPG 040-50 gripper via Fairino SDK commands:
```python
GRIPPER_MODE = "move_gripper"
GRIPPER_ID = 1
GRIPPER_OPEN_POS = 0
GRIPPER_PICK_OPEN_POS = 0
GRIPPER_RELEASE_OPEN_POS = 0
GRIPPER_CLOSE_POS = 38
GRIPPER_SPEED = 40
GRIPPER_FORCE = 40
GRIPPER_MAX_TIME_MS = 3000
GRIPPER_BLOCK = 1
GRIPPER_TYPE = 0
```
Parameters overview:
- `GRIPPER_OPEN_POS`: Fully opened position.
- `GRIPPER_PICK_OPEN_POS`: Pre-position opening width. Useful to prevent fingers from clipping adjacent chess pieces during down movements.
- `GRIPPER_RELEASE_OPEN_POS`: Opening width used during release.
- `GRIPPER_CLOSE_POS`: Position when holding a piece.
- `GRIPPER_SPEED` & `GRIPPER_FORCE`: Speed and force limits.

Test the gripper configuration manually:
```bash
python tests/05_gripper_manual/manual_gripper_close_positions.py --real --positions 33 38
```

### 5.8. AI Chess Engine Selection
```python
ENGINE_TYPE = "CLOUD"      # Options: CLOUD, LOCAL, HYBRID
CLOUD_API_URL = "https://tuongkydaisu.com/api/engine/bestmove"
CLOUD_TIMEOUT_SEC = 6
```
- `CLOUD`: Connects to a remote API (internet connection required).
- `LOCAL`: Runs UCCI chess engine locally on the host machine.
- `HYBRID`: Uses the cloud API as the primary solver and falls back to local execution if the API times out.

### 5.9. Simulation Integration API
```python
SIMULATION_API_URL = "https://tuongkydaisu.com"
SIMULATION_TOKEN = "your-api-token"
```
Replace placeholder tokens with your active credentials. Avoid committing sensitive API tokens to public version control repositories.

## 6. Physical Setup & Calibration

### 6.1. Calibrating the Chessboard Teaching Points
Define the four outer corners of the active board area on your robot controller:

| Teaching Point | Map Position | Physical Reference |
|---|---|---|
| `R1` | `(0,0)` | Corner cell at Black's Left Rook position |
| `R2` | `(8,0)` | Corner cell at Black's Right Rook position |
| `R3` | `(8,9)` | Corner cell at Red's Right Rook position |
| `R4` | `(0,9)` | Corner cell at Red's Left Rook position |

Notes:
- Position the tool center point (TCP) exactly at the center of the target cell.
- Ensure the Z height is uniform across all teaching points to establish a flat plane coordinate system.
- Maintain consistent tool orientation (Euler angles) for all points.

Verify the computed cell dimensions and system alignment:
```bash
python tests/03_robot_math/test_cell_size_from_teaching_points.py
```

### 6.2. Auxiliary Teaching Positions
- `HOMECHESS`: The idle resting position where the robot returns after completing its move, preventing the arm from blocking the camera view.
- `R_Trash`: The trash bin coordinate where captured pieces are dropped. If not taught, the system falls back to `CAPTURE_BIN_X/Y/Z` in `config.py`.

### 6.3. Testing Robotic Motion Manually
*Always test motion scripts using dry run parameters first before committing to physical movement.*
```bash
# Verify center board movement
python tests/04_robot_motion_manual/manual_move_center_safe.py --dry-run
python tests/04_robot_motion_manual/manual_move_center_safe.py --real --speed 20

# Test targeting corner cells
python tests/04_robot_motion_manual/manual_move_board_positions.py --cells 0,0 8,9 --real --speed 20
```

## 7. Vision Dataset Training

The vision module uses a binary occupancy model (detecting only the presence or absence of a piece). The exact identity of the piece is maintained by tracking board state memory (FEN).

### 7.1. Capturing Images & Video
Launch the camera feed viewer:
```bash
python tests/00_camera/droidcam_ui.py
```
Output streams are captured to `assets/droidcam_outputs/`. Save clean gameplay video files to `assets/videos/`.

### 7.2. Labeling the Dataset
An interactive semi-automated tool labels video frames:
```bash
python tests/01_yolo_dataset_tools/autolabel_yolo.py
```
Outputs are written in YOLO structure to `assets/custom_dataset/`.
Keyboard & mouse inputs:
- `s`: Save labels and load next frame.
- `a` / `d`: Previous / next frame navigation.
- `r`: Trigger YOLO auto-inference.
- `c`: Clear all bounding boxes on current frame.
- `Left Drag`: Draw new bounding box.
- `Right Click`: Delete hovered bounding box.
- `Corner Drag`: Adjust bounding box dimensions.

### 7.3. Dataset Evaluation
Check dataset balance and counts:
```bash
python tests/01_yolo_dataset_tools/dataset_stats.py
```

### 7.4. Training YOLO
```bash
yolo detect train \
  model=yolo11m.pt \
  data=assets/custom_dataset/data.yaml \
  epochs=80 \
  imgsz=640 \
  batch=8 \
  name=xiangqi_occupancy
```
After training finishes, save the resulting weights file:
```bash
cp runs/detect/xiangqi_occupancy/weights/best.pt assets/models/best.pt
```

### 7.5. Debugging the Vision Pipeline
To test difference snapshot detection between baseline states:
```bash
python tests/02_yolo_pipeline_debug/yolo_pipeline_debug.py \
  --start assets/sample_images/start.JPG \
  --t1 assets/sample_images/t1.JPG \
  --t2 assets/sample_images/t2.JPG
```

## 8. Operating the System

### 8.1. Running in Dry Run Mode
1. Ensure `DRY_RUN = True` in `config.py`.
2. Run `python main.py`.
3. Interact with the Pygame chessboard using mouse drag-and-drop to simulate human moves. The system triggers the AI solver and updates the board automatically.

### 8.2. Running in Production Mode
1. Ensure `DRY_RUN = False` in `config.py`.
2. Verify:
   - YOLO model weights are located at `assets/models/best.pt`.
   - Camera video stream is active and reachable.
   - The calibration file `assets/perspective.npy` is present and aligned.
   - Robot controller is connected and online.
   - Teaching points are taught and verified.
3. Run `python main.py`.

## 9. Game Logic & Workflows

### 9.1. The T1 & T2 Vision Sequence
- **T1 Baseline:** Captured state representing the board layout before a turn begins. Contains occupancy grids and frame timestamps.
- **T2 Snapshot:** Captured when the user presses `SPACE` after completing a physical move.
- The system evaluates T1 and T2 difference maps. On successful move validation, the internal board state updates, and the game switches to the AI's turn.

### 9.2. AI and Robotic Movements
1. FEN string sent to the active AI Engine.
2. AI returns the optimal target move.
3. System saves a rollback recovery state.
4. Robot coordinates are computed via bilinear interpolation, and motion commands are sent to the manipulator.
5. The robot places the piece and updates the T1 baseline before prompting for the user's next turn.

### 9.3. Rollback & Undo Actions
Pressing `Z` or clicking `UNDO STEP` on the UI reverts:
- Board layouts.
- FEN configurations.
- Move history lists.
- Vision baseline T1 occupancy records.

*Note: Rollback does not undo physical moves on the board. You must return physical pieces to their previous coordinates manually before resuming.*

## 10. Key Bindings & UI Controls

| Control | Action |
|---|---|
| `SPACE` | Captured snapshot (T2) and evaluates human move |
| `Z` / `UNDO STEP` | Reverts the last game and vision state |
| `New Game` | Resets game states for a new match |
| `Surrender` | Resigns the current game |
| `Q` | Exits the camera view and main program loop |

## 11. Git & Version Control Best Practices

To avoid commits containing heavy assets:
- **Exclude**: Heavy dataset folders, raw video recordings, training run output directories (`runs/`), local engine executables, and sensitive credential tokens in `config.py`.
- **Include**: Core codebase files inside `src/`, clean calibration scripts inside `tests/`, custom dataset descriptor YAML configs, and clear system documentation.
